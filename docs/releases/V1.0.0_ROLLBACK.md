# Trazaloop v1.0.0 · Rollback

Qué hacer cuando el despliegue de producción sale mal.

> **Alcance Ruta A.** Este documento cubre la reversión del **despliegue
> técnico** (`V1.0.0_ROUTE_A_SCOPE.md`). No contempla reversión de pagos,
> suscripciones ni analítica, porque esas funciones **no existen** en
> v1.0.0.
>
> La reversión de los **documentos legales** es un procedimiento aparte
> (`scripts/release/v1/rollback-legal-v2.sql`) y está **formalmente
> aplazada**: no se ejecuta hasta que exista texto jurídico aprobado y
> publicado.

> **Regla de oro:** revertir la **aplicación** es barato, inmediato y
> reversible. Revertir la **base de datos** no lo es. Empieza siempre por
> lo primero y solo baja al segundo nivel si el problema está de verdad en
> los datos.

---

## 0. Antes de tocar nada

1. **Anota la hora** y qué se estaba haciendo.
2. **Captura el error**: pantalla, logs de Vercel, logs de Supabase.
3. **Decide el nivel** con la tabla de abajo.
4. **Avisa** a quien corresponda antes de revertir algo visible.

| Síntoma | Nivel | Tiempo |
|---|---|---|
| Error de UI, texto equivocado, página rota | **1 · Detener** | segundos |
| La aplicación no arranca o falla al autenticar | **2 · Deployment** | 1–2 min |
| Apunta al proyecto Supabase equivocado, falta una variable | **3 · Variables** | 2–5 min |
| Datos corruptos o borrados en producción | **4 · Base** | horas |
| Archivos perdidos o expuestos | **5 · Storage** | variable |

---

## 1. Detener el despliegue

**Si el deployment todavía está construyéndose:**

Vercel → Deployments → el deployment en curso → **Cancel**.

**Si ya está publicado y hay que sacarlo de circulación ya:**

Vercel → Project Settings → **Domains** → reasignar el dominio de
producción al deployment anterior que funcionaba.

Esto no borra nada y es reversible en un clic.

⚠️ **No** pauses el proyecto de Supabase. Dejaría sin servicio también a
cualquier otro consumidor y no arregla un problema de aplicación.

---

## 2. Volver al deployment anterior

Vercel → **Deployments** → localiza el último deployment **Ready** que
funcionaba → menú `⋯` → **Promote to Production**.

- [ ] El dominio definitivo sirve el deployment anterior.
- [ ] La aplicación carga y el login funciona.
- [ ] Se anota qué commit quedó en producción.

**Esto NO revierte la base de datos.** Si el deployment fallido escribió
datos, siguen ahí. Ver nivel 4.

**Desde la CLI**, si se prefiere:

```bash
npx vercel ls                       # listar deployments
npx vercel promote <deployment-url> # promover uno anterior
```

---

## 3. Restaurar variables de entorno

Si el problema es de configuración (proyecto equivocado, variable
ausente, kill switch mal puesto):

1. Vercel → Settings → Environment Variables → ámbito **Production**.
2. Corregir el valor.
3. **Crear un deployment nuevo.** Vercel inyecta las variables en tiempo
   de build: cambiar una variable **no** afecta a los deployments ya
   construidos.

   Deployments → `⋯` → **Redeploy**, con «Use existing Build Cache»
   **desactivado**.

4. Verificar sin exponer valores:

   ```bash
   npm run precheck:env -- --env=production --expect-project-ref=<PROD_REF>
   ```

Valores de referencia de Production:

| Variable | Valor correcto |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | `https://<PROD_REF>.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | pública, de **producción** |
| `SUPABASE_SECRET_KEY` | secreta, de **producción** |
| `TEXTILES_MODULE_ENABLED` | `true` |
| `ACTIVE_ORG_COOKIE_SECRET` | el de producción, **distinto** al de staging |
| `NEXT_PUBLIC_SITE_URL` | dominio real de producción (un `*.vercel.app` de producción es válido; nunca el de staging) |

⚠️ **Si Production quedó apuntando al proyecto de staging:** es el peor
caso de configuración. Corrige la URL y las claves **antes de que se
registre ningún dato**, redespliega y verifica con `precheck:env` y con
`verify-empty-production.sql`. Si ya se escribieron datos reales en
staging, trátalos como datos de producción a rescatar: no ejecutes
`cleanup:staging` bajo ningún concepto.

⚠️ Si se sospecha que una clave quedó expuesta: **rótala en Supabase**
(Project Settings → API) y actualiza la variable. Rotar invalida la
anterior.

---

## 4. Restaurar la base de datos

⚠️ **Nunca se restaura encima del proyecto dañado.** Se restaura a un
proyecto **nuevo**, se valida, y solo entonces se redirige la aplicación.

Prohibido en todos los casos:

- ❌ `supabase db reset --linked`
- ❌ `supabase migration repair`
- ❌ `DELETE`/`TRUNCATE` improvisados en producción
- ❌ Editar una migración histórica

### Procedimiento

```bash
# 1. Localizar el punto de restauración
#    Supabase → Database → Backups (automáticos diarios / PITR)
#    o tu propio dump: pg_dump -Fc

# 2. Crear un proyecto Supabase NUEVO (igual que en el despliegue inicial)

# 3. Restaurar sobre el proyecto nuevo
pg_restore --clean --if-exists -d "$NUEVO_DB_URL" produccion_YYYY-MM-DD.dump
#    o, con backup gestionado: Supabase → Backups → Restore, indicando el
#    proyecto destino nuevo.

# 4. Validar el proyecto restaurado ANTES de dirigir tráfico
npm run verify:prod
npx supabase migration list          # 0001–0102, sin divergencias

# 5. Apuntar Vercel Production al proyecto nuevo
#    (URL + claves) y crear un deployment nuevo.

# 6. Volver a validar
npm run precheck:env -- --env=production --expect-project-ref=<NUEVO_REF>
```

- [ ] El proyecto restaurado tiene las migraciones `0001`–`0102`.
- [ ] Las semillas globales están completas.
- [ ] Los datos de empresa son los esperados en el punto de restauración.
- [ ] Se documenta la **ventana de datos perdida** (entre el backup y el
      incidente) y se comunica a las empresas afectadas.

⚠️ **Los archivos de Storage NO están en el dump de PostgreSQL.** El dump
contiene la metadata de `storage.objects`, no los bytes. Ver nivel 5.

## 5. Comprobar Storage

Tras cualquier restauración, la metadata y los archivos físicos pueden
haber quedado desalineados.

```sql
-- Todos los buckets deben seguir siendo PRIVADOS
select id, public from storage.buckets order by id;

-- Cuántos objetos declara la base
select bucket_id, count(*) from storage.objects group by bucket_id order by 1;
```

Contrastar contra lo que se ve en el panel → Storage.

| Situación | Qué significa | Qué hacer |
|---|---|---|
| Metadata sin archivo | La base cree que existe un archivo que ya no está | La descarga fallará. Identificar los afectados y pedir a la empresa que vuelva a subir la evidencia. **No** borres la metadata sin registrar cuál era. |
| Archivo sin metadata | Objeto huérfano, invisible para la app | Consume cuota. Inventariar antes de decidir. |
| Un bucket aparece **público** | Fallo grave de seguridad | Pasarlo a privado **de inmediato** y revisar los accesos registrados. |

- [ ] Los tres buckets (`evidences`, `organization-assets`,
      `trazadocs-documents`) son privados.
- [ ] Una descarga legítima desde la app funciona.
- [ ] Una URL directa sin firmar **no** funciona.
- [ ] Se ha registrado cualquier desalineación encontrada.

---

## 6. Mantener staging operativo

Staging debe seguir funcionando durante todo el incidente: es donde se
reproduce y se corrige el problema.

- [ ] Vercel **Preview** sigue apuntando al proyecto de **staging**.
- [ ] Las variables de Preview no se han tocado.
- [ ] El proyecto Supabase de staging **no** se ha pausado ni borrado.
- [ ] `npm run cleanup:staging` **no** se ha ejecutado durante el
      incidente. Staging puede contener la reproducción del fallo, y
      posiblemente datos rescatados si Production apuntó ahí por error.

Si el CLI quedó enlazado a producción:

```bash
npx supabase link --project-ref <STAGING_REF>
npx supabase projects list          # confirmar el enlace
```

⚠️ Deja el CLI enlazado a **staging** cuando termines. Así, un comando
ejecutado por inercia no toca producción.

---

## 7. Después del incidente

- [ ] Escribir qué pasó, cuándo se detectó y qué lo resolvió.
- [ ] Si hubo pérdida de datos: ventana exacta y empresas afectadas.
- [ ] Si se rotó alguna clave: confirmar que todos los entornos usan la
      nueva.
- [ ] Reproducir el fallo en staging y añadir una prueba de regresión que
      lo habría detectado.
- [ ] Actualizar `V1.0.0_PRODUCTION_READINESS.md` si el procedimiento tenía
      un hueco.
