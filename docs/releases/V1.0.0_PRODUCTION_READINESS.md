# Trazaloop v1.0.0 · Puesta en producción

Procedimiento completo para llevar Trazaloop v1.0.0 a un entorno de
producción limpio.

> **Nada de este documento se ha ejecutado.** Es un procedimiento para que
> lo siga una persona, paso a paso, con confirmación explícita en cada
> punto marcado con ⚠️.

> ## Este documento cubre el DESPLIEGUE TÉCNICO
>
> v1.0.0 sigue la **Ruta A — lanzamiento esencial**
> (`V1.0.0_ROUTE_A_SCOPE.md`), que separa dos hitos:
>
> | Hito | Qué es | Lo cubre |
> |---|---|---|
> | **A · Despliegue técnico** | Infraestructura creada, migrada, verificada y desplegada, **sin usuarios externos** | **Este documento** |
> | **B · Apertura comercial** | Registro público disponible y producto anunciado | `V1.0.0_ROUTE_A_SCOPE.md` §9 |
>
> Completar este procedimiento cumple el **hito A**. **No** habilita por sí
> solo la apertura comercial: esa conserva sus propios gates (paquete
> jurídico aprobado y SMTP personalizado probado).

## 2. Arquitectura staging / production

**Decisión: se crea un proyecto Supabase NUEVO para producción. Staging NO
se convierte en producción ni se purga para reutilizarlo.**

Motivos: staging conserva su valor como entorno de pruebas; una base
recién creada no arrastra datos, usuarios ni objetos de Storage
olvidados; y ningún error de limpieza puede tocar producción.

```
                    ┌──────────────────────────────┐
  rama de trabajo → │ Vercel · Preview             │ → Supabase STAGING
                    │  (deploy por rama/PR)        │    (proyecto actual)
                    └──────────────────────────────┘

                    ┌──────────────────────────────┐
  rama main       → │ Vercel · Production          │ → Supabase PRODUCTION
                    │  (dominio definitivo)        │    (proyecto NUEVO)
                    └──────────────────────────────┘
```

| | Preview | Production |
|---|---|---|
| Proyecto Supabase | Staging (actual) | Nuevo |
| Datos | De prueba, desechables | Reales |
| `TEXTILES_MODULE_ENABLED` | `true` | `true` |
| Se puede limpiar | Sí, con `npm run cleanup:staging` | **Nunca** |
| Suites RLS | Sí | **Nunca** |

Los dos proyectos **jamás** comparten claves ni el
`ACTIVE_ORG_COOKIE_SECRET`.

## 4. Backup

**Antes de crear producción** — respaldo de staging, porque a partir de
aquí se manipula la configuración del CLI de Supabase:

```bash
# Base de staging
pg_dump "$STAGING_DB_URL" -Fc -f staging_$(date +%F).dump

# Estado de enlace del CLI (para poder restaurarlo)
cp -r supabase/.temp supabase/.temp.bak 2>/dev/null || true
```

**Producción recién creada** no necesita respaldo previo (está vacía),
pero **sí** debe tener backups automáticos activados antes de recibir la
primera empresa. Ver `docs/BACKUP_RESTORE.md`.

## 5. Crear el proyecto Supabase de producción

### 5.1 Crear el proyecto

Panel de Supabase → **New project**:

- **Organization**: la de Trazaloop.
- **Name**: `trazaloop-production` (o el nombre acordado).
- **Database password**: fuerte, generada al azar, guardada en el gestor

- **Region**: la más cercana a las empresas usuarias.
- **Plan**: uno con backups automáticos diarios.

⚠️ Este paso lo hace una persona en el panel. No se automatiza.

### 5.2 Obtener el project ref

Project Settings → General → **Reference ID**.

Es la cadena de `https://<project-ref>.supabase.co`. **No es un secreto**
(viaja en cada petición del navegador), pero anótalo: se usa en todos los
pasos siguientes. En este documento se escribe `<PROD_REF>`.

Anota también, por separado, el `<STAGING_REF>`.

⚠️ **Confirma en voz alta que `<PROD_REF>` ≠ `<STAGING_REF>`** antes de
seguir. Todo lo que viene puede escribir en la base.

### 5.3 Enlazar el repositorio temporalmente

```bash
# 1. ¿A qué proyecto está enlazado ahora?
npx supabase projects list

# 2. Enlazar a PRODUCCIÓN — pide confirmación explícita

# 3. VERIFICAR que el enlace es el esperado, antes de cualquier push
```

⚠️ **Comprueba que el proyecto marcado es `<PROD_REF>` y no staging.**
Si no lo es, detente y vuelve a enlazar.

## 6. Migraciones

### 6.1 Dry-run: ver qué se aplicaría

```bash
npx supabase migration list
```

Esperado en un proyecto nuevo: los **94 archivos** de migración locales
(`0001`–`0102`; la numeración salta de `0006` a `0015` por motivos
históricos, no falta nada) aparecen como **locales sin aplicar**, y la
columna remota está vacía.

```bash
# Ensayo sin aplicar: imprime el SQL que se ejecutaría
npx supabase db push --dry-run
```

⚠️ Revisa la salida. Debe empezar en `0001_extensions.sql` y terminar en
`0102_t9g_qa_finalizer_closure.sql`. Si menciona alguna migración
desconocida, o menos de las esperadas: **detente**.

### 6.2 Aplicar

```bash
npx supabase db push
```

**Prohibido en cualquier circunstancia:**

- ❌ `supabase db reset --linked`
- ❌ `supabase migration repair`
- ❌ Editar una migración histórica para «arreglar» un fallo

Si `db push` falla a mitad: **no repares nada**. Anota el error, borra el
proyecto de producción recién creado (está vacío, no hay datos que
perder), corrige la causa en el repositorio y empieza de nuevo desde 5.1.

### 6.3 Comprobar que local y remoto coinciden

```bash
npx supabase migration list
```

Cada migración debe aparecer con versión **local y remota**. No debe haber
ninguna solo-local ni solo-remota.

```bash
# Contraste independiente, por SQL
psql "$PROD_DB_URL" -c \
  "select count(*), min(version), max(version) from supabase_migrations.schema_migrations;"
```

- [ ] `max(version)` = `0102`
- [ ] No existe `0103`

## 8. Superadministrador oficial

El superadministrador es la única cuenta que debe existir en producción
antes de la primera empresa.

⚠️ **No se crean membresías falsas.** El superadministrador es
`platform_staff`, no miembro de ninguna organización. La consola de
plataforma funciona sin pertenecer a ninguna empresa.

Procedimiento controlado:

1. **Crear la cuenta** desde `/register` en el dominio de producción, con
   el correo corporativo oficial. Aceptar los documentos legales.
2. **Promoverla** a superadministrador, con la conexión directa del
   operador:

   ```sql
   -- Sustituye el correo. Ejecutar UNA sola vez.
   insert into public.platform_staff (user_id, is_superadmin)
   select id, true from auth.users where email = 'admin@tudominio.com'
   on conflict (user_id) do update set is_superadmin = true;
   ```

3. **Verificar**:

   ```sql
   select count(*) from public.platform_staff where is_superadmin is true;
   -- debe devolver exactamente 1
   ```

4. **Anotar el correo** en el gestor de secretos del equipo: es el valor de
   `KEEP_AUTH_EMAILS` en cualquier operación futura de limpieza.

- [ ] Exactamente **1** superadministrador.
- [ ] Su correo está anotado.
- [ ] No se creó ninguna organización durante este paso.

#### SMTP — gate del hito B, no del hito A

| | |
|---|---|
| **Hito A · despliegue técnico** | ✅ **Puede completarse SIN SMTP personalizado.** No hay usuarios externos: solo el superadministrador, cuya cuenta se crea de forma controlada |

## 10. Configuración de Vercel

### 10.1 Variables de Production

Settings → Environment Variables → ámbito **Production únicamente**:

| Variable | Valor |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | `https://<PROD_REF>.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Clave pública de **producción** |
| `SUPABASE_SECRET_KEY` | Clave secreta de **producción** |
| `TEXTILES_MODULE_ENABLED` | `true` |
| `PUBLIC_REGISTRATION_ENABLED` | **`false`** — registro público cerrado para el hito A |
| `ACTIVE_ORG_COOKIE_SECRET` | Secreto **nuevo**: `openssl rand -base64 32` |
| `NEXT_PUBLIC_SITE_URL` | `https://app.tudominio.com` |

ℹ️ **El distintivo «Ambiente staging» ya NO depende del dominio.** Desde
v1.0.0 el ambiente lo decide la variable de sistema que inyecta Vercel
(`VERCEL_TARGET_ENV` / `VERCEL_ENV`), no el nombre de `NEXT_PUBLIC_SITE_URL`
(`lib/env.ts` · `resolveDeploymentEnvironment`). Por tanto:

- Un despliegue **Production** sobre un dominio `*.vercel.app` es válido y
  **no** muestra el distintivo.
- `NEXT_PUBLIC_SITE_URL` es solo para construir enlaces (reset de
  contraseña, invitaciones, compartición de pasaportes). Debe apuntar al
  dominio real de este ambiente, pero ya no es una fuente de autoridad
  sobre el tipo de despliegue.
- Vercel define `VERCEL_TARGET_ENV`/`VERCEL_ENV` automáticamente. No las
  configures a mano. Si algún día despliegas Production **fuera** de Vercel,
  declara `VERCEL_ENV=production` explícitamente o se mostrará el distintivo.

⚠️ Las **siete** variables de arriba son obligatorias en Production (y las
mismas siete en Preview). `ACTIVE_ORG_COOKIE_SECRET` y `NEXT_PUBLIC_SITE_URL`
las consume el código del producto: la primera firma la cookie de empresa
activa, la segunda construye los enlaces absolutos.

⚠️ **`SUPABASE_DB_URL` NUNCA se configura en Vercel.** Es solo para
verificaciones locales del operador.

### 10.2 Variables de Preview (no se tocan)

Preview sigue apuntando a **staging** y exige **las mismas seis variables**
que Production, pero con los valores de staging. Verificar que no se ha
cambiado por error:

- `NEXT_PUBLIC_SUPABASE_URL` → `https://<STAGING_REF>.supabase.co`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` → clave pública de **staging**
- `SUPABASE_SECRET_KEY` → clave secreta de **staging**
- `TEXTILES_MODULE_ENABLED` → `true`
- `PUBLIC_REGISTRATION_ENABLED` → `true` (o `false` si se quiere probar el modo cerrado)
- `ACTIVE_ORG_COOKIE_SECRET` → el de staging, **distinto** del de producción
- `NEXT_PUBLIC_SITE_URL` → la URL de staging

El distintivo «Ambiente staging» aparece en Preview automáticamente porque
Vercel marca esos despliegues como `preview` — sin depender del dominio.

### 10.3 Comprobar la presencia de variables

```bash
# Producción (hito A: el registro debe estar CERRADO)
npm run precheck:env -- --env=production --expect-project-ref=<PROD_REF>

# Preview / staging
npm run precheck:env -- --env=preview --expect-project-ref=<STAGING_REF>

# Declarar explícitamente el estado esperado del registro (opcional):
npm run precheck:env -- --env=production --expect-project-ref=<PROD_REF> \
    --expect-registration=disabled
```

Esta herramienta comprueba **presencia**, nunca valores, y no imprime
ninguna clave.

⚠️ Vercel inyecta las variables **en tiempo de build**. Cambiar una
variable **no** afecta a los deployments existentes: hay que crear un
deployment nuevo.

### 11.1 Registro público — CERRADO por configuración

Desde v1.0.0 existe el kill switch server-only
**`PUBLIC_REGISTRATION_ENABLED`**. Para el hito A debe valer **`false`**.

Con el registro cerrado:

- `signUpAction` **no llama** a `auth.signUp`: no se crea usuario, ni
  organización, ni membresía, ni se envía correo.
- `/register` muestra una pantalla controlada, **sin formulario**.
- Los enlaces «Crear cuenta» de la portada y del login pasan a «Solicitar
  acceso» / canal de contacto.
- **El login sigue funcionando** con normalidad, incluido el
  superadministrador.
- Las **personas invitadas** sí pueden crear su cuenta: el servidor
  verifica que la invitación exista, siga pendiente, no haya expirado y
  corresponda a ese correo.

Verificación tras el deployment:

- [ ] `PUBLIC_REGISTRATION_ENABLED=false` en Production.
- [ ] `npm run precheck:env -- --env=production …` en verde (falla si el
      registro está habilitado en Production sin declararlo explícitamente).
- [ ] `/register` **no** muestra formulario.
- [ ] `/login` funciona y permite entrar al superadministrador.
- [ ] `auth.users` contiene **exactamente 1 cuenta**.
      `verify-empty-production.sql` ya falla si aparece cualquier otra.

⚠️ **Cambiar la variable exige un deployment nuevo**: Vercel las inyecta en
tiempo de build.

⚠️ El kill switch **no es un mecanismo de autorización** y **no resuelve**
los demás gates: SMTP personalizado y paquete jurídico aprobado siguen
abiertos por separado. Ver `V1.0.0_ROUTE_A_SCOPE.md` §11.
