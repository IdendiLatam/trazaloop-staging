## 1. Decisión de diseño

En una propuesta inicial se planteó incluir el mercadeo dentro de la
aceptación general de los documentos legales. **Esa opción queda
descartada.**

El consentimiento de mercadeo debe implementarse de forma
**completamente independiente** de la aceptación legal.

### 1.1 Razón

Si el mercadeo se agrupa con la aceptación de términos y privacidad, el
consentimiento deja de ser libre y específico: el usuario **debe** aceptar
los documentos para usar el servicio, y arrastraría el mercadeo sin poder
separarlos. Además, revocar el mercadeo obligaría a tocar la aceptación
legal, que es un registro histórico inmutable.

---

## 2. Requisitos del consentimiento

El consentimiento de mercadeo debe ser:

| # | Requisito |
|---|---|
| 1 | **Casilla separada**, independiente de la aceptación legal |
| 2 | **Opcional** |
| 3 | **Desmarcada por defecto** |
| 4 | **No necesaria** para crear ni utilizar la cuenta |
| 5 | De **finalidad específica** (comunicaciones comerciales sobre Trazaloop) |
| 6 | **Revocable** en cualquier momento, sin coste ni justificación |
| 7 | **Registrado**: usuario, fecha, versión del texto, origen y estado |
| 8 | Con **mecanismo de retiro** en cada mensaje y en las preferencias de la cuenta |

Negar o revocar este consentimiento **no puede** producir ninguna
degradación del servicio contratado.

## 4. Separación estricta de otras comunicaciones

Este consentimiento **NO debe mezclarse jamás** con:

- autenticación y confirmación de cuenta;
- recuperación de contraseña;
- avisos de seguridad;
- invitaciones de equipo;
- notificaciones necesarias del servicio (cambios legales, vencimiento del
  acceso Demo, límites de almacenamiento);
- soporte y respuestas a tickets.

Esas comunicaciones son **necesarias para la ejecución del servicio**, se
envían con independencia del consentimiento de mercadeo y **no llevan
opción de baja**, porque sin ellas el servicio no puede prestarse.

### 4.1 Matriz de clasificación

| Comunicación | Tipo | ¿Requiere consentimiento? | ¿Lleva baja? |
|---|---|---|---|
| Confirmación de correo | Necesaria | No | No |
| Recuperación de contraseña | Necesaria | No | No |
| Invitación a un equipo | Necesaria | No | No |
| Aviso de seguridad | Necesaria | No | No |
| Cambio de documentos legales | Necesaria | No | No |
| Respuesta a un ticket | Necesaria | No | No |
| **Novedades y contenidos** | **Mercadeo** | **Sí** | **Sí** |
| **Invitaciones a eventos** | **Mercadeo** | **Sí** | **Sí** |
| **Ofertas comerciales** | **Mercadeo** | **Sí** | **Sí** |

> **Zona gris marcada para revisión jurídica:** una comunicación sobre una
> funcionalidad nueva puede leerse como informativa o como promocional. El
> criterio propuesto es: si su finalidad principal es **vender o
> promocionar**, es mercadeo. La validación corresponde al área jurídica
> (punto M-03).

## 5. Requisito funcional para desarrollo

> **No implementado.** Ver gaps G-11, G-12 y G-13.

### 5.1 Modelo de datos propuesto

Registro independiente de `user_legal_acceptances`, que **no debe
modificarse** por ser un histórico inmutable.

Campos mínimos por evento de consentimiento:

| Campo | Descripción |
|---|---|
| `user_id` | Usuario titular |
| `purpose` | Finalidad (`marketing`) |
| `granted` | `true` = otorgado · `false` = revocado |
| `consent_version` | Versión del texto mostrado |
| `source` | Origen: `registro`, `preferencias`, `enlace_baja`, `soporte` |
| `occurred_at` | Fecha y hora del evento |
| `ip_address`, `user_agent` | Prueba de la manifestación |

**Append-only**: cada otorgamiento y cada revocación son un registro nuevo.
El estado vigente es el evento más reciente. Nunca se sobrescribe ni se
borra el historial.

### 5.2 Puntos de captura

1. **Registro** — casilla opcional desmarcada.
2. **Preferencias de la cuenta** — pantalla donde ver y cambiar el estado
   actual en cualquier momento.
3. **Enlace de baja en cada mensaje comercial** — debe registrar la
   revocación con `source = enlace_baja`.

### 5.3 Criterio de aceptación técnica

- [ ] La casilla aparece **desmarcada** en el registro.
- [ ] Crear la cuenta **sin marcarla** funciona con normalidad.
- [ ] El estado se puede consultar y cambiar desde las preferencias.
- [ ] Revocar deja registro nuevo y **no borra** el otorgamiento previo.
- [ ] Tras revocar, no se envía ningún mensaje comercial.
- [ ] Las comunicaciones necesarias del §4 siguen llegando tras revocar.
- [ ] Cada mensaje comercial incluye enlace de baja funcional.
- [ ] El consentimiento de mercadeo **no** aparece en el muro de aceptación
      legal.
